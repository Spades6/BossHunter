# 项目介绍

## 一句话

BossHunter 是一个本地优先的 AI 求职工作流：让 AI 做岗位预筛、匹配分析、沟通草稿和状态整理，把是否投递、是否回复、是否发送简历的决定留给人。

## 为什么做

求职最消耗人的往往不是某一个难题，而是一串重复小事：反复打开岗位、判断是否值得看、重新组织招呼语、记住跟进到哪一步、收到“发份简历”后再改一版材料。

常见自动化思路会直接走向“更多、更快地海投”。BossHunter 做了相反的产品判断：AI 应该扩大人的判断能力，不应该替人做不可逆的投递决定。

所以产品把工作拆成两类：

- AI 擅长的：硬条件预筛、完整 JD 与简历的匹配分析、排序、沟通草稿、回复意图识别、简历内容重排。
- 人必须保留的：是否推进岗位、是否发送消息、是否回复 HR、是否发送附件简历。

## 产品闭环

BossHunter 的真实工作流是：

> 岗位采集 → 硬条件预筛 → AI 深度评分 → 人工确认 → 个性化招呼语 → 低频发送 → HR 回复监测 → 定制简历 → 人工发送

Web 工作台把它从一串脚本变成可观察、可停止、可恢复的任务：用户能看到评分理由和风险、选择部分岗位、查看漏斗、处理发送失败和待回复事项。

## 这次比赛新增了什么

原产品强调本地隐私，但这也意味着评委如果没有本地 Chrome、招聘平台登录和 AI Key，就无法真正体验。

比赛版新增了隔离的“评委演示模式”：

- 一份明确标注为虚构的匿名简历。
- 6 条模拟 JD，包含推荐、谨慎和应过滤三种情况。
- 固定、可复现的两阶段评分结果，不依赖临时 API。
- 可勾选岗位的人工确认点。
- 个性化招呼语、状态漏斗与 HR 要简历后的定制简历预览。
- 全程不请求账号、真实简历、API Key 或招聘平台登录，也不会发出任何消息。

这不是一张静态介绍页。评委需要亲自点击并做选择，产品状态会随决策推进。

## 技术实现

- Python 3.10+ 负责 CLI、任务编排、AI 服务、浏览器会话、SQLite 数据与 Bottle API。
- React、TypeScript、Vite 与 Tailwind CSS 负责 Web 工作台和评委沙盒。
- 本地 Browser Runtime 通过 CDP 连接用户已登录的 Chrome；它不会代替用户登录。
- AI 服务层支持 Anthropic 与 OpenAI 兼容协议，配置与密钥留在用户本地。
- 任务运行器支持状态快照、停止信号、人工确认等待、监测队列与错误反馈。
- GitHub Actions 构建只包含前端沙盒的 GitHub Pages 版本，公网环境不带真实后端或用户数据。

## 难点不在“调一次模型”

真正困难的是把一条跨越浏览器、AI、数据库和人的长链路做成可控系统：

- 评分被拆成低成本预筛与深度分析，减少无意义模型调用。
- 生成内容不能直接变成外部动作，必须经过人工检查点。
- 长任务需要随时停止、保留已入库结果，并把失败变成可处理状态。
- Chrome、招聘平台页面和 AI 服务随时可能断开，前端必须给出明确的恢复动作。
- 定制简历只能重排和改写已有事实，不能为了匹配岗位发明经历。

## 产品边界

BossHunter 不鼓励无人值守海投，不宣传绕过平台检测，也不承诺获得面试。第三方招聘平台自动化可能受到其用户协议限制；真实模式只建议个人求职期间本地、短期、低频使用，并由使用者在敏感动作前确认。
